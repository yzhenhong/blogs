# 跨端开发选型指南

跨端开发不是“写一次代码，在所有平台完全一致”。更准确的目标是：在可接受的平台差异下，共享尽可能多的业务逻辑，同时保留目标平台需要的体验和能力。

本专题覆盖四种常见方案：

- [UniApp](/cross-platform/uni-app.md)：以 Vue 语法为主，覆盖小程序、H5 和移动 App
- [Taro](/cross-platform/taro.md)：支持 React/Vue，重点覆盖小程序和 H5
- [React Native](/cross-platform/react-native.md)：使用 React 开发 iOS 与 Android 原生界面
- [Electron](/cross-platform/electron.md)：使用 Web 技术开发 Windows、macOS 与 Linux 桌面应用

## 先按目标平台选择

| 目标 | 优先评估 | 原因 |
| --- | --- | --- |
| 微信等多个小程序 + H5 | UniApp、Taro | 对小程序组件、路由和发布链路支持成熟 |
| 小程序为主，团队熟悉 Vue | UniApp | Vue 上手成本低，DCloud 工具与插件生态完整 |
| 小程序为主，团队熟悉 React | Taro | React 语法和工程体系衔接自然 |
| iOS + Android，重视原生交互 | React Native | 渲染原生组件，原生模块扩展能力强 |
| Windows + macOS + Linux | Electron | Chromium 行为一致，Web 组件生态丰富 |
| 网站可安装、系统能力要求低 | PWA | 无需单独维护桌面安装包 |

先确认目标平台，再比较框架。React Native 和 Electron 都叫“跨端”，但一个主要解决移动端，一个解决桌面端，通常不是同一道选择题。

## 核心维度对比

| 维度 | UniApp | Taro | React Native | Electron |
| --- | --- | --- | --- | --- |
| 主要平台 | 小程序、H5、iOS/Android | 小程序、H5、React Native | iOS、Android | Windows、macOS、Linux |
| 常用语法 | Vue | React 或 Vue | React | 任意 Web 框架 |
| UI 渲染 | 按目标编译/运行 | 按目标编译/运行 | 原生组件 | Chromium DOM |
| Web 代码复用 | 高 | 高 | 中等 | 高 |
| 原生体验上限 | 中等 | 中等 | 高 | 适合桌面 Web 风格 UI |
| 原生能力扩展 | 插件与原生扩展 | 插件与原生模块 | 原生模块、TurboModule | Node.js、Electron API、原生模块 |
| 平台一致性 | 受小程序规范差异影响 | 受小程序规范差异影响 | 受 iOS/Android 控件差异影响 | Chromium 层面一致性高 |
| 产物与运行成本 | 取决于目标端 | 取决于目标端 | 接近原生 App | 安装包与内存占用较大 |

表格只能用于第一轮筛选。最终决定应由一个包含关键页面、登录、存储、网络请求和一项原生能力的最小原型验证。

## 不要只比较“代码复用率”

### 1. 交互是否符合平台习惯

移动端需要处理返回手势、安全区域、软键盘、权限和前后台切换；桌面端需要处理窗口、菜单、鼠标键盘、文件拖放和系统托盘。强行让不同平台长得完全一样，往往会牺牲体验。

更实用的复用边界是：

- 共享接口类型、数据校验、业务规则和状态模型
- 视图组件只在交互模式接近的平台间共享
- 导航、权限、文件、通知等平台能力通过适配层隔离
- 为平台差异保留明确的实现目录，不在业务代码里散落大量判断

```text
src/
├─ core/               # 可共享的业务规则与类型
├─ services/           # 网络、存储等接口定义
├─ platforms/
│  ├─ weapp/           # 小程序实现
│  ├─ native/          # iOS/Android 实现
│  └─ desktop/         # 桌面实现
└─ features/           # 按业务功能组织页面和状态
```

### 2. 团队能否维护原生边界

框架封装不了所有平台差异。遇到推送、蓝牙、音视频、后台任务、支付、系统权限和第三方 SDK 时，仍可能进入原生工程。

评估团队能力时应问：

- 能否阅读 Android/iOS 构建日志和原生代码？
- 能否处理证书、签名、应用商店审核与隐私清单？
- 能否维护 Electron 的安装、自动更新和安全策略？
- 出现框架插件不兼容时，是等待上游还是自行修复？

### 3. 第三方能力是否真的可用

不要只看插件市场的搜索结果数量。选择关键插件时至少验证：

- 最近是否仍在维护
- 是否支持当前框架和目标平台版本
- 是否支持目标 CPU 架构
- 许可证能否用于商业项目
- 是否能处理失败、权限拒绝和后台恢复
- 插件停止维护后是否有替代方案

### 4. 发布链路是否匹配团队

| 平台 | 发布时需要重点处理 |
| --- | --- |
| 小程序 | 平台审核、分包体积、隐私接口、基础库版本 |
| iOS | Apple 证书、Provisioning Profile、App Store 审核 |
| Android | 签名、不同应用市场、系统版本与厂商差异 |
| 桌面端 | 安装包、代码签名、公证、自动更新、杀毒软件误报 |
| H5/PWA | 浏览器兼容、缓存更新、HTTPS、离线策略 |

## 选型流程

### 第一步：写清硬约束

将“最好支持”与“必须支持”分开：

```text
必须支持：微信小程序、H5
关键能力：扫码、支付、文件上传
体验要求：首屏 2 秒内可交互
团队情况：4 名前端，主要使用 React
交付要求：8 周上线，之后每两周迭代
```

有了硬约束，很多方案会自然排除，不需要围绕框架热度争论。

### 第二步：做风险原型

原型不要只做计数器。应优先验证最可能失败的部分：

1. 最复杂的核心页面和长列表性能
2. 登录、权限拒绝与登录状态恢复
3. 一项最关键的原生或平台 API
4. 开发、构建、真机运行和安装包生成
5. 弱网、离线、前后台切换与异常恢复

### 第三步：记录量化结果

| 指标 | 记录方式 |
| --- | --- |
| 开发效率 | 完成原型的有效工时、平台专属代码量 |
| 性能 | 首屏时间、交互延迟、滚动帧率、峰值内存 |
| 产物 | 小程序分包大小、App/安装包体积 |
| 稳定性 | 冷启动、权限拒绝、断网后的成功恢复次数 |
| 维护性 | 调试工具、错误定位时间、关键插件维护状态 |

### 第四步：保留退出路线

框架选择不是不可逆的，但需要提前降低迁移成本：

- 业务规则写成不依赖 UI 框架的 TypeScript 模块
- API schema、数据迁移和错误码保持稳定
- 将平台 API 封装到少量适配器中
- 不让核心数据只存在于某个框架专属存储格式
- 对关键流程保留自动化测试

## 通用工程实践

### 平台能力适配

先定义业务需要的接口，再分别实现：

```ts
export interface FilePicker {
  pick(options: { accept: string[] }): Promise<{
    name: string
    size: number
    uri: string
  } | null>
}
```

业务层只依赖 `FilePicker`，而不是直接依赖 `uni.chooseFile`、Taro API、React Native 模块或 Electron IPC。这样可以集中测试权限、取消和错误处理。

### 统一错误模型

平台 API 的错误格式通常不同。进入业务层前转换为稳定结构：

```ts
export type AppErrorCode =
  | 'PERMISSION_DENIED'
  | 'USER_CANCELED'
  | 'NETWORK_UNAVAILABLE'
  | 'UNSUPPORTED'
  | 'UNKNOWN'

export class AppError extends Error {
  constructor(
    public code: AppErrorCode,
    message: string,
    public cause?: unknown,
  ) {
    super(message)
  }
}
```

“用户取消选择文件”不应当被当作系统故障上报；权限拒绝则需要提供进入系统设置或重新授权的路径。

### 测试分层

- 业务规则：用单元测试覆盖，可在所有平台复用
- UI 组件：测试状态和关键交互，不依赖真实系统 API
- 平台适配器：通过真机或目标系统做集成测试
- 核心流程：在每个正式支持的平台做端到端测试
- 发布产物：从安装包或小程序体验版开始测试，不只测试开发模式

### 持续集成

每次合并至少执行类型检查、单元测试和目标平台构建。发布任务应固定 Node.js、包管理器、框架、原生 SDK 和构建镜像版本，签名材料只从 CI 的 Secret 注入。

## 常见误区

### 一套 UI 适配所有平台

业务逻辑可以高度共享，交互不一定适合共享。桌面端的悬停、右键和快捷键在移动端不存在；移动端底部导航和手势也不适合直接搬到桌面端。

### 只在浏览器模拟器中测试

模拟器无法完整覆盖真机性能、权限弹窗、软键盘、后台回收、文件系统和厂商差异。关键流程必须在最低支持版本和至少一台真实设备上验证。

### 遇到差异就堆条件编译

少量差异可以使用条件编译；大量散落的 `if platform` 会让代码无法推理。差异持续增长时，应抽取平台适配器或平台专属组件。

### 版本越新越应该立即升级

框架升级需要同时检查插件、原生 SDK、构建工具和发布平台。先阅读迁移说明，在独立分支完成全平台构建与回归，再进入正式项目。

## 推荐学习顺序

1. 明确目标平台和关键系统能力。
2. 阅读对应专题的基础、生命周期和路由章节。
3. 完成一个包含请求、存储、权限和列表的最小应用。
4. 补充平台专属能力，并在真机或目标系统验证。
5. 从正式产物完成一次完整发布演练。
6. 再考虑状态管理、性能优化和高级架构。
